# 宠物寄放与培养

先读 `petshop.go`、`pet.go`、`fight.go` 的窗口状态、宠物JSON、升级与 `endMember` 结算，以及客户端NPC列表/原生操作镜像。区分随身五槽与可扩展仓库；不要把仓库容量增加误做随身槽增加或协议批量传输全部宠物。

## 状态与费用

培养和普通寄放共享Pool，持久化标记仅表示当前正在培养；领取时清除，普通再寄放不继续。普通旧JSON缺少标记应保持不培养。检查所有PetShop的pool_flg分支及老菜单索引，提供培养和领取路径。

确认窗口仅是报价。执行时在世界事件循环重新检查当前宠物、费用、容量、战斗/交易、骑乘、送信和家族守护兽等限制，全部通过后同次转移宠物并扣费；取消、重复确认和失败不应改金币/数量。费用与宠物沿用同一人物存档，不给每只培养宠物另建goroutine或SQL写路径。

## 分页与身份

页数根据实际仓库存量，至少1页；clamp页码并把规范页写回窗口状态。行号限于当前页及实际存在行，拒绝负数、跨页值、空行和重复/过期窗口。长名字、MaxHP和培养标签可能自动折行，必须验证渲染行与回传索引一致，不能只测试短名字。

## 经验与持久化

高等级敌人无奖励时，先检查 `data.EnemyExp` 的原版表是否截断，再追踪 `battle.NewEnemy`、`KillExp` 与最终 `endMember`。原版 `enemyexptbl.h` 有完整1..200级，不能拟合前100项来补后100项；保留历史异常值。表外等级按项目明确的兼容策略延伸，覆盖当前资源最高等级与溢出边界。审计加载后的每条自动奖励敌人和其全部等级范围，区分模板数量、区域引用与实际地图数；显式0事件在等级折算后仍须为0，不能用“至少1”抬升。真实敌人结算测试应沿用模板计算，不手工覆盖 Fighter.Exp 掩盖根因。

从战斗最终人物权威奖励派生培养经验，再交给原生petGainExp成长。按任务约定整数舍入，避免先整除造成多损；每只培养宠物各得同份，不扣人物奖励。普通寄放、非战斗加经验、PvP、失败/逃跑、人物未获经验都不能误发。正常/快速/后台/组队复用唯一结算入口，防止重复奖励。

即使人物未携带出战宠，也必须把更新的Pool序列化并存档；验证保存和重新登录后的标记、等级、经验、属性。沿用现有全局/个体等级上限与声望逻辑，不另造升级算法。按容量上限评估单次有界循环，避免遍历中发送全仓库协议或逐宠存盘。

## 证据

先红后绿覆盖容量边界、500只分页、费用不足、禁止状态、取消/重放、普通与培养隔离、升级/上限和持久化。真实Chromium使用匹配最终ELF与真实HTTP/WebSocket，通过原生UI确认转移/翻页/领取，并用战斗奖励和落盘JSON核对经验；不注入假页面数据。移动竖横屏模拟单独记录，不能当实体设备认证。

最后核对源码、内嵌客户端、ELF、ZIP及摘要一致。未新增素材时不生成空素材补丁，继续附带既有补丁。
